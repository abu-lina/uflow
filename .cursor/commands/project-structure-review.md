# Next.js project structure review and cleanup

Review the project file structure and organize it. Follow these steps:

## 1. Structure analysis

Examine the project structure and identify:

- Files and folders in incorrect locations
- Inconsistent naming conventions (kebab-case vs camelCase vs PascalCase)
- Duplicate or redundant files
- Unused components, utilities, or assets
- Missing essential directories or configuration files
- Improperly organized routes in the app directory
- Mixing of server and client components without clear separation

## 2. Next.js 14 App Router checks

Verify the structure follows proven approaches:

- Proper use of `/app` directory structure
- Correct placement of `layout.tsx`, `page.tsx`, `loading.tsx`, `error.tsx`
- Route groups `(group-name)` used appropriately
- API routes in `/app/api`
- Static assets in `/public`
- Shared components location: check if using `/components` or `/app/_components`
- Proper separation of server vs client components (verify 'use client' directives)
- Correct use of private folders with `_` prefix
- Parallel and intercepting routes if applicable

## 3. Code organization

Check organization of:

- **Components**: Reusable UI components (verify structure: `ui/`, `common/`, `shared/`, `layout/`)
- **Features**: Feature-specific modules combining UI, hooks, and services
- **Lib/Utils**: Helper functions, utilities, constants (verify separation: `lib/` for general utilities, `utils/` for pure functions)
- **Types**: TypeScript types and interfaces
- **Hooks**: Custom React hooks
- **Actions**: Server actions (if using)
- **Styles**: Global styles, Tailwind config, CSS modules
- **Config**: ESLint, TypeScript, Next.js configs
- **Tests**: Test files location and naming (`__tests__/` vs co-located)
- **Assets**: Images, fonts, icons organization

## 4. Path aliases and imports

Verify path alias configuration:

- Check `tsconfig.json` paths match actual directory structure
- Verify aliases are used consistently (`@/components`, `@/lib`, `@/utils`, etc.)
- Identify any hardcoded relative paths that should use aliases
- Check for missing aliases that would improve import clarity

## 5. Architecture alignment

Verify structure matches the defined architecture:

- **Components**: Pure, reusable UI only (no business logic)
  - `ui/`: Atomic design elements
  - `common/`: Generic small components
  - `shared/`: Larger shared UI blocks
  - `layout/`: Layout containers
- **Features**: Feature modules combining UI, hooks, and services
- **Services**: External service wrappers (Supabase, APIs)
- **Lib**: General utilities (Supabase client, PWA helpers)
- **Utils**: Pure utility functions and error helpers
- **Providers**: React context providers
- **Types**: Global TypeScript types and interfaces

## 6. Ask before making changes

Before suggesting restructuring, ask about:

- The purpose of any unclear files or directories
- Whether certain components are shared across routes or route-specific
- Preferred naming conventions for the team/project
- Whether to use barrel exports (index.ts files)
- How to handle legacy pages if migrating from pages router
- Whether certain files are generated by tools and shouldn't be moved
- Preferences for organizing tests (co-located vs separate `/__tests__` dir)
- Whether using any monorepo structure or specific tooling
- Whether the current `src/` folder structure should be maintained

## 7. Provide restructuring plan

After getting clarification, provide:

- A clear before/after directory tree visualization
- Step-by-step migration instructions
- Any necessary import path updates (especially for path aliases)
- Scripts or commands to help with the restructuring
- Warnings about potential breaking changes
- Updated path aliases for `tsconfig.json` if needed
- Verification that changes align with existing architecture rules

## 8. Optional enhancements

Ask if suggestions are wanted for:

- Path aliases configuration (verify existing `@/*` aliases are optimal)
- Barrel exports for cleaner imports
- `.env` file organization
- `.gitignore` updates
- Additional tooling (Prettier, Husky, etc.)

Start by analyzing the current project structure using the file tree. List findings and ask for clarification on anything unclear before proposing changes.
