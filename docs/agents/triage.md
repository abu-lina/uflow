# Triage: raw issues → ready lanes

Move raw incoming issues through a state machine until they are either agent-ready, waiting on the reporter, rejected, or handed to a human. Run this before a lane is proposed. The foreman calls this for every unlabelled or `needs-triage` issue it encounters.

Every comment posted to the issue tracker during triage **must** start with:

```
> *This was generated by AI during triage.*
```

## Roles

**Category** (pick one):

- `bug` — something is broken
- `enhancement` — new feature or improvement

**State** (pick one):

- `needs-triage` — evaluation in progress
- `needs-info` — waiting on reporter for more information
- `ready` — fully specified, acceptance criteria in "when I do X, I see Y" form, agent-ready
- `ready-for-human` — needs human judgment, design decisions, or external access
- `wontfix` — will not be actioned

State transitions: unlabelled → `needs-triage` → `needs-info` / `ready` / `ready-for-human` / `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. The maintainer can override at any time.

## 1. Show what needs attention

Query and present three buckets, oldest first:

1. **Unlabelled** — never triaged.
2. **`needs-triage`** — evaluation started but not resolved.
3. **`needs-info` with reporter activity since last triage notes** — needs re-evaluation.

```bash
gh issue list --state open --no-assignee \
  --json number,title,labels,updatedAt \
  --jq '.[] | "\(.number)\t\([.labels[].name]|join(","))\t\(.title)"'
```

Show counts and one-line summary per item.

## 2. Triage a specific issue

### 2a. Gather context

Read the full issue body, comments, labels, author, and dates. Parse any prior triage notes so you don't re-ask resolved questions. Run two checks:

- **Redundancy**: search the codebase for an existing implementation of the requested behaviour by domain concept (not just the issue's wording). If found, it is an already-implemented `wontfix` — point to where it lives.
- **Prior rejection**: read `.out-of-scope/*.md` and surface any that resembles this request.

### 2b. Recommend

Tell the maintainer your category and state recommendation with brief reasoning, plus a codebase summary relevant to the request. Wait for direction.

### 2c. Verify the claim

For a **bug**: reproduce it from the reporter's steps. Note what you ran and what happened (confirmed, failed, or insufficient detail). A confirmed reproduction makes a much stronger agent brief.

For an **enhancement**: confirm the feature doesn't already exist (see 2a redundancy check).

### 2d. Grill (if needed)

If acceptance criteria are missing or fuzzy, run a grilling session — one round of numbered questions at a time, each with a recommended answer. Update `CONTEXT.md` and ADRs inline as decisions land.

### 2e. Apply the outcome

**`ready`** — post an agent brief (template below). Label the issue `ready`.

**`ready-for-human`** — post the same brief structure, noting why it can't be delegated (judgment call, external access, design decision, manual testing). Label accordingly.

**`needs-info`** — post triage notes (template below). Label the issue `needs-info`.

**`wontfix`** — close the issue:

- _Already implemented_: point to where it lives. Do not write to `.out-of-scope/` (that is for rejected requests, not built ones).
- _Rejected (bug)_: polite explanation, close.
- _Rejected (enhancement)_: write to `.out-of-scope/<concept>.md`, link from a comment, close.

**`needs-triage`** — apply the label. Optional comment if there is partial progress.

## Agent brief template

Post this as a comment when moving to `ready` or `ready-for-human`:

```markdown
> _This was generated by AI during triage._

## Agent Brief

**Category:** bug / enhancement
**Summary:** one-line description of what needs to happen

**Current behavior:**
What happens now.

**Desired behavior:**
What should happen after the work is complete. Be specific about edge cases.

**Key interfaces:**

- `TypeName`: what needs to change and why
- `functionName()`: what it currently returns vs. what it should return

**Acceptance criteria:**

- [ ] When I do X, I see Y
- [ ] When I do A, I see B

**Out of scope:**

- Thing that should NOT be changed in this issue
```

Acceptance criteria must be in "when I do X, I see Y" form — observable, not procedural. No file paths or line numbers; they go stale.

## Needs-info template

```markdown
> _This was generated by AI during triage._

## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1 (specific and actionable)
- question 2
```

Capture everything resolved during grilling under "established so far". Questions must be specific; "please provide more info" is not acceptable.

## Quick state override

If the owner says "move #42 to ready", trust them and apply the label directly. Confirm the role change, then act. Skip grilling. If there is no agent brief yet, ask whether to write one.

## Resuming a session

If prior triage notes exist on the issue, read them, check whether the reporter answered outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.

## What you never do

- Post a triage comment without the AI-generated disclaimer.
- Move an issue to `ready` without an Acceptance Criteria section in the body or an agent brief comment.
- Triage issues the owner or the workflow agents created — triage is for raw external requests only.
