This declaration was visible to every downstream agent and was correctly followed by DevOps.

- **Both plans were purely corrective (no design invention required).** Scope clarity enabled fast, low-rework execution from Implementer through UAT.

## Process Improvement Recommendations

### P1 — Critical

**TOKEN-BUDGET: Front-load skill reads at phase start**
DevOps and other documentation-heavy phases should load required skills as the *first* action before any git operations or file reads. The commit skill and document-lifecycle skill should both be read in the opening parallel batch. Skill reads are cheap relative to their value; doing them late risks budget exhaustion mid-phase.

**SKILL-PATH: Use `tool_search_tool_regex` before reading any skill file**
The wrong skill path (`agent-output/document-lifecycle/SKILL.md` vs `.github/skills/document-lifecycle/SKILL.md`) caused a tool failure and wasted tokens. The correct pattern: use `tool_search_tool_regex` with `document.lifecycle` to locate the skill before reading it, or always use the known base path `.github/skills/<name>/SKILL.md`.

### P2 — Important

**LIFECYCLE-CLOSE-IN-COMMIT: Include doc moves in the Stage 1 commit**
Plan 039's lifecycle doc closure and Stage 1 deployment doc were not in the Plan 039 feature commit. The `chore(docs)` orphan sweep is becoming a recurring pattern. The fix: DevOps Stage 1 procedure should explicitly stage lifecycle doc renames (git renames to `closed/`) and the deployment doc in the same commit as the feature files — or immediately as the first commit if the feature was committed by a previous phase.

**TIMESTAMP-DISCIPLINE: Capture real UTC clock time at each phase boundary**
Plan changelogs contain impossible timestamp sequences (Plan 040 QA at 08:37Z precedes Code Review at 09:30Z). The correct process: at the start of each phase, note the actual UTC time and record it as the phase entry timestamp. Do not estimate or copy-paste prior timestamps. This is the only way retrospective timeline analysis is accurate.

### P3 — Improvement

**UAT-DEFERRED-RISK: Convert deferred UAT findings into named next-plan recommendations**
FIND-CR-040-1 (operational logging for unconfigured WhatsApp) was deferred at Code Review and again at UAT with no owner. If a LOW finding is worth documenting, it is worth a one-line "Recommend: Plan TBD — Add warn log to `getWhatsAppContactUrl()`" in the UAT handoff notes, so it surfaces in the next planning cycle rather than being buried in a closed doc.

**DEPENDABOT: Create a dedicated security maintenance plan**
GitHub reports 2 HIGH / 1 MODERATE pre-existing Dependabot findings on the default branch. These are pre-existing and `npm audit --audit-level=high` returns 0 locally, but the production-visible signal is concerning. A dedicated security plan (Plan 041?) should be created to audit and resolve these before the next feature release.

## Technical Patterns (Secondary)

These are documented for completeness; they are implementation details, not process improvements.

- **Server-side prop pattern** (Plan 040): Server component reads `process.env` → constructs derived value → passes as prop to client component. This is the correct Next.js 15 App Router pattern for injecting server-only config into client-rendered UI without `NEXT_PUBLIC_` exposure.
- **Null-safe CTA pattern**: Both plans used "return null; suppress CTA" over "display placeholder or broken link" as the degradation mode for missing configuration. This is the correct pattern for optional contact links.
- **Single-query lookup with fallback** (Plan 039): `getProviderName()` returns `null` on any error; callers apply language-appropriate fallback. This is safe for background dispatch (one extra query per dispatch at low frequency).

## Lessons Learned Summary

### For Future Plans in This Domain (Outreach / Owner Decision)

1. When adding required props to a React component (`whatsappUrl`), immediately audit all test renders of that component for missing prop updates. Bulk-update test renders in the same implementation pass.
2. The owner-decision page is a server component wrapper over a client component — all configuration should flow through the server component as props, never via `NEXT_PUBLIC_`.

### For Workflow Design

1. The Critic's job of converting architectural intent into unambiguous acceptance criteria (FIND-040-1) prevented a class of implementation-time shortcut. This is high-leverage Critic work.
2. Code Review surface area matters: FIND-CR-040-2 was only possible because the Code Reviewer read both the new test file AND the existing test file and compared null-path coverage. Reviewers should explicitly check existing test files for coverage gaps on new conditional paths.
