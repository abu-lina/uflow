## Value Statement and Business Objective

**As a** developer working on UFlow, **I want** PWA build outputs to be consistently gitignored **so that** local builds and dev server sessions stop creating phantom `deleted: public/fallback-*.js` diffs that pollute every commit and require repeated manual restoration.

## Problem Statement

`public/fallback-ce627215c0e4a9af.js` is tracked in git, but it is a **build output** generated by `@ducanh2912/next-pwa`. The `.gitignore` already excludes all other PWA build outputs (`sw.js`, `workbox-*.js`, `worker-*.js`, `fallback-development.js`) but inconsistently leaves hashed production fallback files tracked. Every `npm run build` or `npm run dev` session deletes or regenerates this file, causing:

1. Recurring `deleted:` entries in `git status` / `git diff`
2. Accidental staged deletions that break deployed PWA offline fallback
3. Workaround guard scripts (`scripts/guard-fallback-assets.js`) and lint-staged hooks that fight the build system instead of fixing root cause
4. Repeated agent time spent investigating and restoring the file across multiple sessions

### Root Cause

| PWA Build Output         | In `.gitignore`? | Tracked in git? | Consistency |
| ------------------------ | ---------------- | --------------- | ----------- |
| `public/sw.js`           | ✅ Yes           | No              | ✅ Correct  |
| `public/workbox-*.js`    | ✅ Yes           | No              | ✅ Correct  |
| `public/worker-*.js`     | ✅ Yes           | No              | ✅ Correct  |
| `public/fallback-development.js` | ✅ Yes  | No              | ✅ Correct  |
| `public/fallback-*.js` (hashed) | ❌ No    | **Yes**         | ❌ Inconsistent |

The hashed fallback file is the only PWA build artifact that is tracked. The build process (`@ducanh2912/next-pwa` via Workbox) owns this file — it generates it during `next build` and the hash changes when content changes. Committing it to git is fighting the build system.

**Production safety**: The Dockerfile runs `npm run build:standalone` which generates the fallback file. It then copies `public/` into the runtime image. The file does NOT need to be committed — the production build creates it.

## Assumptions

1. The Dockerfile's `npm run build:standalone` generates the fallback file — verified by `COPY --from=builder /app/public ./public` in Dockerfile

3. The guard script (`scripts/guard-fallback-assets.js`) has no other purpose beyond this workaround

## Plan

### Milestone 1: Gitignore Hashed Fallback Files

**Objective**: Make `.gitignore` consistent — all PWA build outputs excluded.

**Tasks**:
1. Add `**/public/fallback-*.js` pattern to `.gitignore` in the existing PWA build outputs section (lines 69–75), replacing the specific `**/public/fallback-development.js` line since the broader glob covers it
2. Add corresponding `**/public/fallback-*.js.map` for source maps consistency

**Acceptance Criteria**:
- `.gitignore` contains `**/public/fallback-*.js` glob
- Glob covers both development and production hashed fallback files

### Milestone 2: Untrack the Committed File

**Objective**: Remove `public/fallback-ce627215c0e4a9af.js` from git index without deleting it from disk.

**Tasks**:
1. Run `git rm --cached public/fallback-ce627215c0e4a9af.js`
2. Verify `git status` shows the file as "deleted" in staging (this is expected — it's being removed from tracking)
3. Verify the `.gitignore` pattern prevents re-tracking

**Acceptance Criteria**:
- File is no longer tracked by git
- File is not re-added by `git add .` due to `.gitignore`
- After a clean `npm run build`, no fallback files appear in `git status`

### Milestone 3: Remove Guard Script and Hooks

**Objective**: Remove the workaround now that root cause is fixed.

**Tasks**:
1. Delete `scripts/guard-fallback-assets.js`
2. Remove `"guard:fallback": "node scripts/guard-fallback-assets.js"` from `package.json` scripts
3. Remove `"*": ["npm run guard:fallback"]` from `package.json` lint-staged config (if present)
4. Remove `'*': ['npm run guard:fallback']` from `lint-staged.config.js`

**Acceptance Criteria**:
- Guard script no longer exists
- No lint-staged or npm script references to `guard:fallback`
- `npm run lint` and pre-commit hooks still work without the guard

### Milestone 4: Verification

**Objective**: Confirm the fix works end-to-end.

**Tasks**:
1. Run `npm run build` — verify no fallback files appear in `git status`
2. Run `npm run dev` — verify no fallback files appear in `git status`
3. Run `git add . && git status` — verify no fallback files staged
4. Confirm `git ls-files public/fallback-*` returns empty

**Acceptance Criteria**:
- Clean `git status` after build (no phantom deletions)
- Build succeeds and generates fallback file in `public/` (it just isn't tracked)
