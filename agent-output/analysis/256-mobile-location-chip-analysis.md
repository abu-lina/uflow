## 4. Clearing the city

- "No city" URL = the section root: `/food` (or `/stores`, `/ummah`) with no `[city]` segment. `buildResultsUrl` omits the segment when `city` is falsy (`src/lib/search-params.ts:19-24`). `?location=` is a legacy transport still read at `ProvidersContent.tsx:158-164`, but new writes go through path segments.
- Desktop clear: the "Everywhere" dropdown option calls `deactivateNearMe()` → `setSelectedLocation(LOCATION_ALL)` → `onLocationChange?.(LOCATION_ALL)` (`SearchBar.tsx:445-460`). `Header.handleLocationChange` maps `''` to `city: null` → `buildResultsUrl` → `/food` (`Header.tsx:136-152`).
- **Reusable seam exists**: `buildResultsUrl({section, city: null, query, filters})` (`src/lib/search-params.ts:9-32`) + `getResultsPathForSection` (`src/config/sectionFilters.ts:115-119`). D2 needs no new route builder for "clear city"; it needs a caller. For "activate Near Me clears city on mobile", `SearchBar.syncUrl`'s pattern (`SearchBar.tsx:214-244`, navigate to section root + `?near_me=1`) is the precedent but lives inside desktop `SearchBarContent`; `ProvidersContent.handleToggleNearMe` (`:229-237`) currently does no navigation and would need the same strip-city-from-path behaviour added (or the logic extracted). For "pick city clears Near Me" on mobile: `/search` submit (`page.tsx:585-596`) builds a city URL but nothing clears `?near_me` state — however since the URL has no `near_me` param, `nearMeFromUrl` (`ProvidersContent.tsx:190`) will be false on landing; only stale in-component state would persist if navigation were client-side without remount.

## 8. Layout risk

- Row markup: `ProvidersContent` → `DiscoveryHeader filterBarSlot` → `DiscoveryFilterBar.tsx:48`: `<div className="flex flex-nowrap items-center gap-2 overflow-x-auto">` — confirmed `overflow-x-auto`, `flex-nowrap`.
- Children: Near Me button (`:49-66`, `shrink-0`, `h-8`), Open Now (`:68-80`, `shrink-0`), then `{adminSlot}` (`:82`) which renders `AdminStatusFilter` for admins. All children are `shrink-0`, so a variable-width city chip inserted **first** will push Open Now (and the admin chip) rightward into scroll on narrow screens — matches the request's claim; safe mechanically but increases horizontal scroll depth.
- Chips are `h-8`, `rounded-md`, uppercase, `font-inter-tight text-sm font-semibold`; a location chip should reuse the same classes. `DiscoveryFilterBar` takes no `t` prop — it calls `useLanguage()` internally (`:36`), so the chip can translate without new plumbing.
- Note: `DiscoveryHeader` only mounts `DiscoveryFilterBar` when `section === 'food'` (`ProvidersContent.tsx:666`) and never when `showGreeting` is true (`:630-661` uses `MobileGreetingHeader` instead) — the chip won't appear on stage-2 greeting surfaces or ummah/stores results without extra work.

## 9. Open decisions for the user (ranked)

1. **What the chip shows while Near Me is active.** With D2 exclusivity, `/food?near_me=1` has no city, so the chip can only ever show "Everywhere" or a city — a visible "Near me" state on this chip duplicates the existing Near Me chip. Options: (a) hide the location chip when `nearMeActive` (zero code beyond a conditional, mirrors desktop merge visually); (b) show it as "Everywhere" (truthful post-D2 since near-me strips the city); (c) merge labels like desktop (`t('suchen.nearMe.chipLabel')`) — cosmetic duplication. Cost is trivial either way; it's a UX call.
2. **Does clearing the city on a results page mean a route change, and to where?** The code answer is `/food` (section root via `buildResultsUrl({city: null})`). Options: always route to section root on "Everywhere" pick; or also let the chip tap itself (not just the Wo picker) clear directly with `router.push(buildResultsUrl({section, city: null, query, filters}))` preserving `q`/`filters`/`status`. Cheap either way, but decides whether the chip needs a second tap target.
3. **Should D2 also clear `localStorage.selectedCity`?** `localStorage.selectedCity` feeds onboarding gating (`navigationUtils.ts:162`), home stage (`useAppStage.ts:130`), `/search` Wo hydration (`page.tsx:421-426`), and create flows — it is _not_ the results-page source of truth. Clearing it on Near Me activation would change onboarding/home behaviour (user's "home city" disappears). Options: (a) leave it stale — results page is unaffected, `/search` re-hydrates the old city into Wo (arguably a feature: "return to my city"); (b) clear it — consistent mental model but silently un-gates onboarding state. Recommend flagging (b) as risky without a separate product decision.
4. **D2 scope: mobile only or desktop too?** Desktop already enforces exclusivity (`SearchBar.tsx:219-220, 249-265`), so D2 is effectively a mobile-only gap. The question worth confirming: should mobile `handleToggleNearMe` (`ProvidersContent.tsx:229-237`) adopt the same navigate-to-section-root behaviour, which is a route change on chip tap (scroll/history implications), vs. merely ignoring the city while active. First option = consistent + truthful URL but full navigation; second = smaller diff but `/food/stuttgart?near_me=1` remains a lying URL.
5. **Notify-me / city-with-no-providers reachability.** The route-through works: `/search` Wo accordion renders `EmptyCityCard` for valid cities with zero providers (`WoCityResults.tsx:243-245`, `page.tsx:429-463`) regardless of entry point, so no decision needed on reachability — but confirm whether `?open=wo` should also be added to the deep-linkable contract (e.g. reused by other entry points) or kept minimal.
6. **Does `open=wo` persist across in-page interactions?** `handleSectionChange` (`page.tsx:541-543`) carries all params forward, and nothing deletes `open`, so a user who taps the chip, then switches to Stores, lands back on Wo-open. Options: delete param on first read (needs an effect + `router.replace`), or accept the persistence (zero code).
